# Лабораторная работа №3. Безопасный CI/CD для NLP-проекта

Проект продолжает ЛР1–ЛР2: классификация англоязычных SMS на ham/spam,
TF-IDF + LogisticRegression, нормализация NFKC/casefold/whitespace.
Новая модель для другой задачи и отдельный CI-сервер не создаются.

## Запуск и порядок pipeline

GitHub Actions: [все запуски](https://github.com/VaisouI/NLP/actions).
Конфигурация: [ci.yml](../.github/workflows/ci.yml).
Один job последовательно выполняет:

1. Checkout без сохранения credentials; Python 3.12.16; установка фиксированных зависимостей.
2. Получение UCI по HTTPS, проверка архива и файлов по эталонам ЛР1, воспроизведение разбиения ЛР2.
3. Ruff, Bandit и pytest (JUnit XML).
4. pip-audit: любая находка, пропуск или операционная ошибка означает отказ.
5. Data gate по отдельной политике.
6. Fit кандидата только на train, сохранение skops и SHA256, повторная проверенная загрузка.
7. Оценка сохранённого кандидата на фиксированном CI-контроле; model gate.
8. Сборка минимального inference-образа.
9. Проверка SHA256 установщика Trivy, отдельные сканирования Dockerfile и образа, security gate.
10. Проверка ненулевого UID и smoke-запуск модели в контейнере.
11. Загрузка диагностических отчётов с `if: always()`, включая неуспешный job.

Все обязательные шаги зависят от предыдущих. Нет `continue-on-error`, подавления
неуспешного кода или альтернативного успешного пути после отказа. Входы
`pull_request_target` не используются. Права workflow — только `contents: read`,
таймаут job — 25 минут. Используемые Actions закреплены полными commit SHA.
Внешним PR не передаются secrets; обязательный pipeline вообще не требует
пользовательских токенов. Запись в registry и deployment в эту работу не входят.

## Данные для CI

Источник: [UCI SMS Spam Collection](https://archive.ics.uci.edu/dataset/228/sms+spam+collection),
DOI [10.24432/C5CC84](https://doi.org/10.24432/C5CC84), авторы Tiago Almeida и
José María Gómez Hidalgo. Тот же снимок, что в ЛР1–ЛР2; лицензия CC BY 4.0.
Архив и исходные SMS остаются вне Git; в логах и публичных отчётах нет текстов SMS.

| Объект | SHA256 |
|---|---|
| Исходный `SMSSpamCollection` | `7d039a24a6083ed9ef0f806ebad56bbb976e3aeb8de05669173bfdc4996c239d` |
| ZIP источника | `1587ea43e58e82b14ff1f5425c88e17f8496bfcdb67a583dbff9eefaf9963ce3` |
| Каноническое разбиение ЛР2 | `501059ed268a2ddd6019bd422ced9d6031374891c633944e791e0042f464834b` |
| `artifacts/ci/control.jsonl` | `491bfa211530d93e191309882e5ccee0611589b434deb95dc7fce1e2d4952cfd` |

Выборка CI — 1025 объектов: ham 897, spam 128. Это отдельные 20% после исключения
недопустимых входов и повторов нормализованного текста, seed 42; train — 3074,
финальный test — 1025. Из финального test метрики в CI не вычисляются.

Формат `lab3-ci-jsonl-v1`: одна запись JSON в строке, UTF-8, завершающий LF,
ключи отсортированы, разделители `,` и `:`, Unicode не экранируется.
Порядок — возрастающие индексы CI в очищенном корпусе ЛР2.

| Поле | Схема |
|---|---|
| `source_row` | Целое неотрицательное число; индекс исходной строки с нуля; уникальное |
| `text` | Непустая строка, до 4096 символов и 16384 байт UTF-8; политика ЛР2 |
| `target` | Ровно `ham` или `spam` |

Политика [data_gate.json](../config/data_gate.json): только эти три поля,
строгие типы, запрет пропусков, null, NaN/Inf, недопустимого Unicode и управляющих
символов, дубликатов ID и нормализованных текстов; ровно 1025 объектов,
доля ham 0,84–0,90, spam 0,10–0,16, файл не больше 1 MiB. Проверяются версия
источника, версия и SHA разбиения, версия формата и SHA самого JSONL.
Дисбаланс сохранён; контрольные диапазоны отражают распределение ЛР2.
Отсутствующие значения отклоняются — заполнение могло бы изменить смысл SMS.

## Модель, baseline и порог

Baseline хранится отдельно в [metrics/baseline_ci.json](../metrics/baseline_ci.json),
его файловый SHA закреплён в [model_gate.json](../config/model_gate.json).
Ни одна команда CI не пишет baseline. Основная метрика одинакова для baseline
и кандидата: binary F1, положительный класс spam, `zero_division=0`.

```text
baseline F1 = 0.9411764705882353
threshold   = baseline × 0.95 = 0.8941176470588235
pass        = candidate F1 >= threshold
```

Несовместимая версия данных/разбиения, другая метрика, роль или объём выборки,
отсутствующее значение, bool, строка вместо числа, NaN/Inf и значение вне [0,1]
отклоняются. Нулевой baseline требует отдельно утверждённого абсолютного порога.
`candidate-metrics.json`, `model-comparison.json` и `model-status.json` содержат
метрики, решение, порог, SHA модели и фактический код возврата.

Модель ЛР2 не размещается в публичном Git. В CI за доли секунды обучается кандидат
с теми же параметрами на том же train (без подбора по CI/test), затем оценивается
сохранённый и повторно загруженный артефакт. Манифест фиксирует связь с исходной
моделью ЛР2 и помечает артефакт как `ephemeral_ci_candidate`. Повторная сериализация
skops может дать другой побайтовый SHA; именно текущий SHA проверяется перед
загрузкой и помещается в отчёт. Исходный baseline остаётся от ЛР2.
Повторяющийся контроль CI не заменяет независимый финальный test.

## Тесты и статический анализ

Сохранены негативные тесты ЛР2: неверные типы/схема/пределы до вызова модели,
нормализация, загрузка skops после проверки целостности, расчёт метрик с заранее
известным ответом и неизменяемость baseline. Дополнены тестами data/model/security
gate, граничного порога, повреждённой копии данных, несовместимой версии,
нечисловой метрики и неполного отчёта сканера. Unit-тесты используют небольшие
фиксированные примеры; сетевые загрузки и обучение на всём корпусе в них отсутствуют.

Ruff: E4, E7, E9, F, Python 3.12, [ruff.toml](../ruff.toml).
Bandit: весь `src/`. В исходной ЛР3 исключений не было; в добавленном API ЛР4
есть два точечных обоснования B104/B310 в [BANDIT_EXCEPTIONS.md](../security/BANDIT_EXCEPTIONS.md).
Полная фиксация приложения и инструментов — `requirements.txt`, включая
Ruff 0.17.3, Bandit 1.9.4, pip-audit 2.10.1 и pytest 9.2.0.
`requirements-runtime.txt` содержит только inference-зависимости и их транзитивное
замыкание; Jupyter, pandas, графики и аудиторы в образ не устанавливаются.

## Docker и security gate

[Dockerfile](../Dockerfile) использует официальный `python:3.12.16-slim-trixie`.
Версия закреплена тегом; digest не закреплён, поэтому обновления базовых слоёв
внутри тега возможны. Использованный image ID и RepoDigests фиксируются в
`docker-inspect.json`. Допускается дальнейшее закрепление проверенного digest.
Явные COPY передают только inference-код, конфигурацию и два файла кандидата.
[.dockerignore](../.dockerignore) разрешает только эти пути: исходные SMS, CI-выборка,
Git, VM, ключи и `.env` в build context не включаются.

Пользователь и группа 10001, shell `nologin`, директива USER. В smoke-проверке
нет сети, запись в корневую ФС запрещена, capabilities сброшены, включён
`no-new-privileges`, заданы пределы памяти, CPU и процессов. Docker socket
и `privileged` приложению не предоставляются. Перед skops-десериализацией
проверяются размер/SHA, версия sklearn и фиксированный список типов; SHA-манифест
хранится отдельно от файла модели и передаётся в образ явно.

Trivy 0.76.1 устанавливается из официального release aquasecurity/trivy.
SHA256 Linux-64bit.tar.gz:
`c7cbe3137fb8a48a17574bede3dd6beb16742d1e9772929940fc90082c39d9c0`.
Установщик не выполняет загруженный shell-код. Версия, время проверки и полные
JSON-отчёты сохраняются. База уязвимостей актуализируется при запуске.

Зависимости: любая находка pip-audit блокирует pipeline, JSON содержит пакет,
версию, ID и доступные исправления. Образ: CRITICAL и неразобранные UNKNOWN блокируют выпуск;
отсутствующая severity тоже трактуется как UNKNOWN. HIGH/ниже сохраняются в отчёте,
но не блокируют по минимальной политике работы. Dockerfile: блокируются все
найденные ошибки конфигурации. Отсутствующий/некорректный результат и ошибка
скачивания базы/сканирования не считаются отсутствием уязвимостей.

Первый реальный запуск обнаружил UNKNOWN у CVE-2026-82560 (`perl-base`),
следующий — новые UNKNOWN для SQLite после обновления базы. UNKNOWN не считается
безопасным. Команда `scan` получает соответствующие опубликованные записи CVE
Program по HTTPS из одного зафиксированного commit cvelistV5. В отчётах сохраняются
полные JSON, URL, commit и SHA256 каждого источника. Используются только CVSS
CNA и CISA-ADP (3.0/3.1/4.0); при нескольких оценках выбирается наиболее строгая
severity. UNKNOWN без валидного CVSS, недоступность источника и несовпадение CVE
дают отказ. Исходный CRITICAL никогда не понижается.

Это обогащение severity из первоисточника, не исключение уязвимости. Исходный
Trivy JSON сохраняется полностью. Для CVE-2026-82560 опубликованный CVSS CISA
равен 7,5 / HIGH; HIGH остаётся в отчёте и допускается минимальной политикой ЛР3.
Доказательства, ограничения и оставшийся риск:
[пример разбора severity](../security/CVE-2026-82560-review.md).

## Локальное воспроизведение

На Linux с Python 3.12 и Docker (в сохранённой VM — от пользователя, которому
администратор разрешил только необходимые операции Docker):

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --only-binary=:all: -r requirements.txt
python scripts/ci/lab3.py prepare
ruff check src/ tests/
python -m bandit -r src/
python -m pytest tests/ -q
python scripts/ci/lab3.py audit
python scripts/ci/lab3.py data
python scripts/ci/lab3.py train
python scripts/ci/lab3.py model
docker build --pull -t ml-project:lab3 .
bash scripts/ci/install_trivy.sh
export PATH="$HOME/.local/bin:$PATH"
python scripts/ci/lab3.py scan
docker run --rm --entrypoint id ml-project:lab3 -u
docker run --rm --network=none --read-only --cap-drop=ALL \
  --security-opt=no-new-privileges --pids-limit=64 --memory=512m --cpus=1 \
  --entrypoint python ml-project:lab3 -m src.smoke --self-test
python scripts/ci/lab3.py smoke
```

Не добавляйте `mluser` в группу Docker только ради CI: группа даёт полномочия,
сопоставимые с root. Для обязательной демонстрации достаточно GitHub-hosted runner.
Системный firewall и SSH сохранённой учебной VM этот workflow не изменяет.

## Три отдельные демонстрации отказа

Рабочий сценарий в `config/ci_scenario.json` — `normal`. Каждый отказ выполняется
отдельным коммитом в отдельной демонстрационной ветке, меняя только это поле.
Сценарии не ослабляют обязательные проверки и не переключают итоговый код на успех.

| Сценарий | Реальное действие | Где pipeline обязан остановиться | Что далее не выполняется |
|---|---|---|---|
| `bad-data` | У временной копии первой записи поле text заменяется на message; оригинал сохранён | Data quality gate | Fit, model gate, build, scan, smoke |
| `weak-model` | Сохранённая LR-модель с нулевыми коэффициентами и отрицательным intercept всегда предсказывает ham; реально оценена на CI, F1=0 | Model quality gate | Build, scan, smoke |
| `security-policy` | После реальных сканирований отдельно проверяется безопасный отчёт с SIMULATED-CRITICAL-001 | Security gate | Non-root/smoke |

Третий сценарий — **имитация входа политики**, не результат сканирования уязвимого
сервиса. Исходник `tests/fixtures/simulated-critical-trivy.json` явно помечен.
Настоящие `pip-audit.json`, `trivy-config.json`, `trivy-image.json` и
`real-image-security-policy.json` сохраняются отдельно; их находки не заменяются.
Никакие реальные секреты и намеренно уязвимые сервисы для демонстрации не нужны.

Ссылки на фактические запуски и их commit фиксируются после выполнения в разделе
ниже. Статус `failed` плюс `skipped` последующих обязательных шагов подтверждается
списком Steps в Actions; диагностический upload при этом должен выполниться.

## Ограничения

SHA256 проверяет соответствие сохранённому снимку, а не достоверность меток или
отсутствие исходного poisoning. CI gate не защищает от администратора репозитория,
который одновременно меняет код, политику и эталон: такие изменения требуют review.
Branch protection и обязательный независимый review предлагаются дополнительно;
этот workflow сам не меняет административные настройки GitHub.
Базы уязвимостей обновляются: ранее прошедший commit может перестать проходить.
Тогда нужно исправить/обновить зависимость или базовый образ и повторить проверки,
а не скрывать код отказа или широко исключать уязвимости.
